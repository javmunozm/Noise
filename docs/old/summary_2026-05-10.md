## Production Pipeline 1 — Designed 8-Family v2 (Hybrid)

**File**: `ml_models/designed_family_predictor.py`  
**Goal**: Maximize coverage (8+ floor, 12+ ceiling) across all 7 simultaneous events.

### Construction
The 8 sets are **static** — derived once via simulated annealing over all C(25,14)=4,457,400 possible events, not over historical draws. Overfitting is impossible by construction.

- **Coverage**: 99.49% of all possible 14-events covered at ≥9 matches
- **Floor guarantee**: 100% of events covered at ≥8 matches
- **12+ ceiling**: 41,280/41,280 provable events (0.9261% of universe)
- **Max pairwise overlap**: 8 (ensures disjoint 12+-neighborhoods)
- Verified by exhaustive 2-swap search + destroy-and-repair (5,000 candidates/set) — no improvement possible within those neighborhoods

### S5 Hybrid Signal Injection
One slot (the most-redundant set by pairwise overlap) is replaced each series by a signal-derived set:

- **Signal formula**: `score[n] = freq_L30[n] − 1.5 × freq_L5[n]`
- Interpretation: numbers warm over 30 draws but NOT peaked in the last 5 (L5-peaked = anti-signal)
- **OOS backtest** (n=29, 3193–3221): hybrid avg E1-best = 9.931 vs v2-static 9.828 (+0.103)
- Replaced slot varies per draw (highest-overlap set to the new signal set)

### Pair Regime Diagnostic (session 32 refinement)
Before generating the prediction, `pair_weight_evaluator.py` flags sets carrying "FROZEN" pairs (pairs absent from recent L20 E1 draws):

- For each of the C(25,2)=300 pairs: `peso = tasa_L20 / baseline_IID`
- Sets ranked by `peso_medio` (avg pair weight across all 91 pairs in the set)
- FROZEN pairs (`peso < 0.5`) trigger number swaps respecting `max_overlap ≤ 8` and novelty
- **OOS impact** (n=31): refined avg=9.968 vs original 9.839 (+0.129), 11+=8 vs 6

## Production Pipeline 2 — FastTree Single Ticket

**File**: `ml_models/fasttree_predictor.py`  
**Bias config**: `ml_models/fasttree_bias.json`  
**Goal**: Best single-ticket prediction for E1, targeting match depth over coverage breadth.

### 7-Stage Architecture

**Stage 1 — LightGBM (FastTree analogue)**
- Label: E1-only appearance (not any-event)
- Training window: rolling last 100 series (distant history hurts E1 signal)
- 14 features per number: recency, FreqLast10/20/50/100, MeanGap, GapStd, AppearancesTotal, Streak, Event1FreqLast10/20/50, MeanCoAppear50, TopCoAppear50 (E1, last 50)
- Hyperparams: 100 trees, lr=0.2, num_leaves=20, min_data_in_leaf=10, seed=42
- Output: normalized probability vector over 1..25

**Stage 2 — Bias Calibration (rank-calibrated)**
- `bias[n] = -(avg_rank_when_in_actual − 13.0) / 13.0`, clipped to [−0.40, +0.40]
- Numbers chronically under-ranked by LightGBM → lifted: **1, 2, 6, 10, 11, 18, 19, 25**
- Numbers chronically over-ranked by LightGBM → suppressed: **5, 9, 13, 16, 20, 21, 23, 24**
- Recalibrate after every ~10 new draws: `python ml_models/fasttree_predictor.py --fit-bias --from <sid-19> --to <sid>`

**Stage 3 — Hot/Cold Signal (L30−1.5×L5)**
- Identical formula to hybrid family signal
- Alpha=0.10 (tested 0.0–0.40; peaks at 0.10, degrades beyond 0.20)
- Blend: `prob[n] *= (1 + 0.10 × (norm_signal[n] − 0.5))`

**Stage 4 — SelectorRefiner (overdue-swap)**
- Borderline zone: bottom 4 of top-14 (swap-out candidates) vs top 6 outside top-14 (swap-in)
- Rank-based, NOT margin-based (LightGBM probs are flatter than C# FastTree; margin approach failed)
- Swap-in gate: `overdue_score(n) ≥ 2.0` → 66.7% accuracy vs 50% base on L20 calibration
- Swap-out gate: requires both not-overdue AND pool also rejects it
- Max 2 swaps per series

**Stage 5 — Pool Model (independent frequency scorer)**
- Multi-window weighted frequency: windows [5, 10, 20, 50, 100], weights [0.35, 0.25, 0.20, 0.12, 0.08]
- Structurally different from LightGBM → genuine disagreement signal
- Used by Polisher (V1) and Auditor (pool top-14 reference)

**Stage 6 — SelectorPolisher (veto bad refiner swaps)**
- V1 PoolDisagreement (weight 0.40): pool rank gap ≥ 10 between swap-in and swap-out
- V2 RawConfidenceMargin (weight 0.35): raw LightGBM prob ratio > 1.05 (swap-out was more confident before bias)
- V3 RecentEvent1Streak (weight 0.25): swap-out drawn ≥3×/last 5; swap-in ≤1×/last 5
- Veto threshold: 0.62 (raised from C# default 0.60 to avoid marginal 2-component fires)
- Minimum 2 components must agree to veto

**Stage 7 — RefinerAuditor (risk/rescue substitution)**
- Risk: StaleAnchor, ClusterImbalance, ContextDrift, SwapInstability
- Rescue: CoverageGapFill, RecentDrawAgreement, MissedByBothModels
- Very conservative: risk_threshold=0.65, min_components=3 (rarely fires on 32-draw OOS)

## Key Engineering Decisions Made Across Sessions

### Data infrastructure
- **MSSQL cache** (`LuckyDb.dbo.Draws`): all data queries go through `ml_models/db_query.py`. Never read raw JSON (≈300k tokens each).
- **EventIndex order bug fixed** (session 27): `merge_all_draws.py` was lex-sorting events within draws, destroying per-event identity. E1=KINO was being displaced to random positions. Fix: insertion-order dedup. All historical scoring is now valid.
- **Filter pool expanded 9×** (session 26): API scrape of 2,417 draws for novelty checking. All 8 v2 sets verified novel vs 14,971-event pool.

### Signal discovery
- **L30−1.5×L5** is the only signal with statistical support: warm-but-not-peaked numbers.
- **HOT-number chasing is anti-signal** on recent regime (L10/L20 hot numbers underperform, p=0.022).
- Date dimensions (DOW, month, day-of-month, year) are all null after Bonferroni correction.
- IID confirmed twice: session 11 (7,516 events) and session 28 (14,978 events). Every history-pattern approach exhausted.

### Architecture decisions
- **E1 focus only**: E2–E7 pay nothing below 14/14. All analysis targets KINO (E1).
- **8 sets, not more**: coverage ceiling at 8 sets; adding more sets doesn't change P(14/14).
- **No hot-number chasing**: confirmed anti-correlated with results; pair hot-regime tool is a *diagnostic* (swap FROZEN pairs OUT), not a predictor.
- **Pair regime tool as diagnostic, not predictor**: cold pairs appear *less* often next draw (p=0.024), counter to gambler's fallacy. Tool's value is flagging structural misalignment, not predicting next numbers.

## What the System Should Achieve

### Minimum expected performance
- **8-family**: ≥9 match on every E1 draw (100% 8+ floor, 99.49% 9+ floor by construction)
- **FastTree**: ≥8.031/14 avg on E1 OOS (+0.191 vs random)
- **Hybrid signal**: +0.10 improvement on E1 best-match vs pure static v2

### Actionable improvement directions (not yet exhausted)

Train result showed 3.80% 12+ vs v2's 0.88% — but OOS failed at 0/30 due to pairwise-overlap bug (sets clustered, near-redundant). Fix was coded (diversity constraint) but not yet executed. This is the highest-priority unexplored direction.
2. **Bias recalibration** (CLAUDE.md directive 8): after series 3225 result, run `--fit-bias --from 3205 --to 3225` to keep the rolling-L20 calibration current. The current bias was fitted on 3193–3224.
3. **OOS FastTree improvement**: current OOS 8.031 avg with max=11 and only 1×11+ in 32 draws. The polisher/auditor components are calibrated conservatively (rarely fire). With more OOS data (n→50+), thresholds can be relaxed to find more improvement candidates.

### Mathematical ceiling (hard limits — cannot be exceeded)
- P(any of 8 sets hits 12+ | E1, one series) = 6.28% (design ceiling, not defect)
- P(14/14 exact match | E1, one series) = 1/4,457,400 = 0.0000002244
- Expected wait for first 14/14 = ~79,597 series ≈ 265 years at 300 draws/year
- The system's value is maximizing coverage per ticket, not defeating the lottery's math
